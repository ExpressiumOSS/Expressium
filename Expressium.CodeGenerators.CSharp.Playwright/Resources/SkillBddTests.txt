# Expressium BDD Tests Skill

This skill governs BDD test authoring for **any project built on the Expressium test automation framework**.
All projects share the same structural conventions; only namespaces and paths differ per project.

---

## Step 0 — Discover the Project Identity

Before writing any files, read `Configuration.json` to identify the project:

```
<root>\<namespace>.Tests\Configuration.json
```

The `Company` and `Project` fields determine the namespace:

```json
{
  "Profiles": {
    "Development": {
      "Company": "Expressium",
      "Project": "Coffeeshop",
      ...
    }
  }
}
```

From `Company = "Expressium"` and `Project = "Coffeeshop"`:

| Purpose | Value |
|---|---|
| Web (application) namespace | `Expressium.Coffeeshop.Web` |
| Tests namespace | `Expressium.Coffeeshop.Web.Tests` |
| Web (application) project folder | `Expressium.Coffeeshop.Web\` |
| Tests project folder | `Expressium.Coffeeshop.Web.Tests\` |

**General pattern:** `{Company}.{Project}.Web` and `{Company}.{Project}.Web.Tests`

> Note: "Web (application) project" refers to the page-object project (`Pages\`, `Models\`, `Controls\`,
> `Services\`). Do not confuse it with the API *tests* (`ApiTests\`) that live inside the Tests project;
> despite the name, the page-object project is `...Web`, not `...Api`.

## Solution Structure

```
<root>\
├── {Company}.{Project}.Web\
│   ├── Pages\              ← Page objects — read to understand available actions
│   ├── Models\             ← Page models — read to know model properties
│   └── Controls\           ← Low-level control wrappers — do not use directly in tests
│
└── {Company}.{Project}.Web.Tests\
    ├── BusinessTests\
    │   ├── Features\       ← OUTPUT: .feature files
    │   ├── Steps\          ← OUTPUT: *Steps.cs files
    │   └── Hooks\          ← BaseHooks.cs — do not modify
    ├── Factories\           ← OUTPUT: *ModelFactory.cs files
    ├── UiTests\            ← Low-level tests for inspiration only — do not replicate
    └── Configuration.json  ← Source of truth for Company/Project/namespace
```

**Namespace templates** (substitute `{Company}` and `{Project}` from Configuration.json):
- Page objects: `{Company}.{Project}.Web.Pages`
- Models: `{Company}.{Project}.Web.Models`
- Steps: `{Company}.{Project}.Web.Tests.BusinessTests.Steps`
- Factories: `{Company}.{Project}.Web.Tests.Factories`

## Workflow: Generating BDD Tests for a New Page

**Step 1 — Read `Configuration.json`** to discover Company and Project names → derive namespaces and folder paths.

**Step 2 — Explore the solution tree** to confirm actual folder names:
```
Filesystem:directory_tree
```

**Step 3 — Read the page object** at `{Web folder}\Pages\{Page}Page.cs`
Note: what `FillForm`, `Click*`, and `Get*` methods exist.

**Step 4 — Classify the page** (see Page Classification section below).
If the page is navigation-only — **stop here**, do not generate any files for it.

**Step 5 — Read the model** at `{Web folder}\Models\{Page}PageModel.cs`
Note: all properties — needed to build the factory.

**Step 6 — Check if factory already exists** at:
`{Tests folder}\Factories\{Page}PageModelFactory.cs`
If it exists and its content is already correct — skip writing it.

**Step 7 — Identify the next available TC block** (see TC Numbering section below).

**Step 8 — Write the files:**

| File | Target path |
|---|---|
| `{Page}.feature` | `{Tests folder}\BusinessTests\Features\{Page}.feature` |
| `{Page}Steps.cs` | `{Tests folder}\BusinessTests\Steps\{Page}Steps.cs` |
| `{Page}PageModelFactory.cs` | `{Tests folder}\Factories\{Page}PageModelFactory.cs` |

**Step 9 — Confirm** each file was written and report the saved paths.

### File Writing Rules
- Always save files directly to the solution using `Filesystem:write_file`
- Derive all paths from `directory_tree` — never guess
- Skip writing a factory if it already exists with correct content
- Never write to `bin\`, `obj\`, or any build output folder

## Page Classification

Before generating any BDD tests, classify the page by inspecting its page object methods:

### Navigation-only pages — SKIP, do not generate BDD tests

A page is navigation-only if its page object contains **only** `Click*` methods that navigate to
other pages, with no form fields, no data entry, and no submittable actions. These pages have no
meaningful business behaviour to validate beyond navigation, which is already covered implicitly
by the `Given I have logged in with valid user credentials` step and the When steps of other features.

**Indicators of a navigation-only page:**
- Only `Click*` methods — no `Set*`, `Get*`, `FillForm`, or `Submit*` methods
- No associated page model (`{Page}PageModel.cs` does not exist)
- The page serves purely as a menu, toolbar, or navigation bar

**Example — `MainMenuBar.cs` is navigation-only:**
```
ClickHome(), ClickProducts(), ClickContactUs(), ClickLogout()
```
No form fields, no model → **do not generate** `MainMenuBar.feature` or `MainMenuBarSteps.cs`.

### Testable pages — proceed with BDD test generation

A page qualifies for BDD tests if it has any of the following:
- A `FillForm(model)` method
- One or more `Set*` methods (data entry fields)
- A submittable action (`ClickSubmit`, `ClickSend`, `ClickLogIn`, etc.)
- An associated page model
- One or more public `BaseTable` properties (read-only data display pages)

### Table-based pages

A page that exposes one or more public `BaseTable` properties but has no form fields, no model,
and no submittable actions is a **table-based page**. It qualifies for BDD tests because the
presence of row data is meaningful business behaviour — it confirms the data loaded correctly.

**Rules for table-based pages:**

- Generate **exactly one scenario**: `View the {Page} Overview`
- No factory is needed — do not create a `{Page}PageModelFactory.cs`
- The `Then` step is **pending** with a scaffolded assertion (use `asserts.GreaterThan` on `GetNumberOfRows()`)
- Navigate to the page via `MainMenuBar` inside the `When` step
- The `Given I have logged in with valid user credentials` step is required

**Feature file template for table-based pages:**

```gherkin
@TC-X000 @PageName @BusinessTests
Feature: PageName
	As a User
	I want to view the [Page Name] page of the web application
	So that I can browse the available [business data]

@TC-X001 @Review
Scenario: View the [Page Name] Overview
	Given I have logged in with valid user credentials
	When I navigate to the [Page Name] page
	Then the [Page Name] overview should be displayed
```

**Step definition template for table-based pages:**

```csharp
[When(@"I navigate to the [Page Name] page")]
public async Task WhenINavigateToThe{Page}PageAsync()
{
    var mainMenuBar = new MainMenuBar(logger, page);
    await mainMenuBar.Click{Page}();

    var {page}Page = new {Page}Page(logger, page);
}

[Then(@"the [Page Name] overview should be displayed")]
public async Task ThenThe{Page}OverviewShouldBeDisplayedAsync()
{
    var {page}Page = new {Page}Page(logger, page);
    //asserts.GreaterThan(await {page}Page.{Table}.GetNumberOfRows(), 0, "Validating the {Page}Page {Table} table contains at least one row of data...");

    throw new PendingStepException();
}
```

## TC Number Assignment

TC blocks are assigned per feature. Before assigning a new block:
1. Scan all existing `.feature` files in `BusinessTests\Features\`
2. Identify the highest TC-X000 block already in use
3. Assign the next block (increments of 1000)

Scenarios within a feature use the block base + sequential offset:
- Feature tag: `@TC-3000`
- Scenarios: `@TC-3001`, `@TC-3002`, `@TC-3003` ...

## Feature File Rules

### File naming
Feature file name matches the page object name without the "Page" suffix:
- `ContactUsPage.cs` → `ContactUs.feature`
- `RegistrationPage.cs` → `Registration.feature`

### Feature-level tags and description
```gherkin
@TC-X000 @PageName @BusinessTests
Feature: PageName
	As a [Actor]
	I want to [Action]
	So that [Benefit]
```

### Scenario-level tags
```gherkin
@TC-X001 @Review
Scenario: ...
```

Status tags: `@Review` (new/unverified), `@Done` (verified), `@Ignore` (skipped).

### Scenario naming convention
Scenario names follow **BDD style** and use **Title Case** for all important words — nouns, verbs,
adjectives, and domain terms. Minor words (articles, prepositions, conjunctions) such as "a", "an",
"the", "with", "when", "for", "of", "to", "and", "or", "in" are written in lowercase unless they
are the first word.

A good scenario name describes:
1. **User action** (the behaviour being exercised)
2. **Context or condition** (the data or state, if relevant)
3. **Clear intent** (what the user is trying to do)

An **outcome qualifier** — "Successful" / "Unsuccessful" — is optional. The default form omits it:
`[Action] [Page Name] with Valid Details`, `... with Missing Details`, `... with Invalid Details`.
A leading "Successful"/"Unsuccessful" is allowed where it aids readability (and appears in some shipped
features such as `Login.feature`); when used, apply it consistently — valid → "Successful ...",
missing/invalid → "Unsuccessful ...". Avoid noisier outcome words like "Correctly", "Fails", or "Passes".

Because each scenario covers exactly one case (no `Examples` rows), the scenario name must name that
case explicitly — `Reject a Search by an Unknown Status`, not `Reject an Invalid Search`.

**Examples:**
```
✅ Scenario: Submit Contact Us with Valid Details          ← default (neutral) form
✅ Scenario: Submit Contact Us with Missing Details
✅ Scenario: Submit Contact Us with Invalid Details
✅ Scenario: Register a New Account with Valid Details
✅ Scenario: Reset the Registration Form
✅ Scenario: Cancel the Registration Process
✅ Scenario: Successful User Login with Valid Credentials    ← optional qualifier, also fine
✅ Scenario: Unsuccessful User Login with Invalid Credentials

❌ Scenario: submit contact us with valid details            ← not Title Case
❌ Scenario: User Submits Correctly and Test Passes           ← noisy outcome words ("Correctly", "Passes")
```

### Maximum 5 scenarios per feature

| # | Type | Required? |
|---|---|---|
| TC-X001 | [Action] with Valid Details (Happy Path) | Always |
| TC-X002 | [Action] with Missing Details (Validation) | Always |
| TC-X003 | [Action] with Invalid Details (Validation) | Always |
| TC-X004 | Reset the [Form] | Only if Reset button exists on page |
| TC-X005 | Cancel the [Action] Process | Only if Cancel button exists on page |

The table shows the default (neutral) scenario names; a leading "Successful"/"Unsuccessful" qualifier is optional (see naming convention above).

Pages without reset/cancel get **3 scenarios only**.
Table-based pages get **1 scenario only** (see Table-based pages section above).

**Exception — service/contract features.** A feature covering an API service rather than a page
(e.g. `Pet.feature` over a `PetService`) legitimately exceeds 5 scenarios, because splitting one
`Scenario Outline` into explicit scenarios multiplies the count. For these, group the scenarios
under `Rule:` blocks and keep the count as low as the behaviour allows. State the deviation when
reporting the generated files. The 5-scenario cap still applies strictly to page-driven features.

### Step writing rules
- The shared login step is `Given I have logged in with valid user credentials` (matching the implemented `LoginSteps` binding). Use it verbatim wherever a scenario needs an authenticated user. An invalid-login variant `Given I have logged in with invalid user credentials` also exists.
- Steps are high-level and business-focused — one When, one Then per action
- No `Background:` blocks
- No separate navigation steps (navigation belongs inside When step definitions)
- No field-by-field low-level steps
- When the same action appears as both a precondition and an action, phrase the two forms so they differ
  only in tense — `Given I have added a new pet to the store with valid details` /
  `When I add a new pet to the store with valid details` — so a single method can carry both bindings
  (see "Reuse one method across equivalent step phrasings")

### Scenario Outline is not used

**Never generate `Scenario Outline` or `Examples` blocks.** Every case gets its own `Scenario` with a
name that states what it covers.

An `Examples` table hides the meaning of each row behind a placeholder. When the rows select different
*behaviours* rather than different *data*, the step definition is forced to branch on the placeholder
value (see "No logical statements in step definitions"), and the feature file stops describing what is
actually tested. Splitting removes both problems: one scenario, one behaviour, one binding, no branching.

> **This rule overrides shipped code.** `Orders.feature` uses a `Scenario Outline`; it predates this
> rule and is not the pattern to copy. Do not "fix" it as a side effect of unrelated work, but do not
> replicate it either.

❌ **Wrong — outline with Examples:**
```gherkin
@TC-6012 @Review
Scenario Outline: Reject an Invalid Request Body when Adding a Pet
	When I attempt to add a new pet to the store with <Details> details
	Then the pet service response status should be <Status>
Examples:
	| Details       | Status |
	| malformed     | 400    |
	| empty         | 400    |
	| wrongly typed | 400    |
```

✅ **Right — one scenario per case:**
```gherkin
@TC-6013 @Review
Scenario: Reject a Malformed Request Body when Adding a Pet
	When I attempt to add a new pet to the store with a malformed request body
	Then the pet service response status should be 400

@TC-6014 @Review
Scenario: Reject an Empty Request Body when Adding a Pet
	When I attempt to add a new pet to the store with an empty request body
	Then the pet service response status should be 400

@TC-6015 @Review
Scenario: Reject a Request Body with a Wrongly Typed Identifier
	When I attempt to add a new pet to the store with a wrongly typed identifier
	Then the pet service response status should be 400
```

**Inline parameters are still fine.** A capture group carrying a plain *value* the step passes straight
through — `When I search the pet catalogue for the status available` bound by `for the status (.*)` — is
correct and preferred over near-duplicate bindings. The test is whether the step branches on the value:
if it does, split the step (see below); if it just forwards it, keep the parameter.

### Advanced Gherkin features

- **`Rule:` blocks** group related scenarios under a business rule. Optional, but preferred when a
  feature covers more than one distinct rule — and effectively required for service/contract features,
  where they carry the structure an `Examples` table would otherwise have implied. A short descriptive
  line under the `Rule:` is allowed.
  ```gherkin
  Rule: Rejecting Invalid Request Bodies

  @TC-6013 @Review
  Scenario: ...
  ```
- **Step `DataTable`** — for structured multi-value input **within a single scenario**, where the table
  is genuinely one payload (e.g. a basket of several line items ordered together), not a set of separate
  cases. Bound with a `DataTable` parameter and mapped via `dataTable.CreateInstance<T>()` into a small
  private class. Do not use a `DataTable` to smuggle in what an `Examples` table would have done.
  ```gherkin
  	When I add multiple pieces of coffee to the shopping cart
  		| Brand                  | Pieces |
  		| La Ceiba Huehuetenango | 2      |
  ```
  Keep data variation modest — prefer a couple of rows that prove the behaviour, not exhaustive combinations.

### Feature file template

```gherkin
@TC-X000 @PageName @BusinessTests
Feature: PageName
	As a User
	I want to [perform action] through the [page name]
	So that I can [benefit]

@TC-X001 @Review
Scenario: [Action] [Page Name] with Valid Details
	Given I have logged in with valid user credentials
	When I [action] [Page Name] with valid details
	Then I should see the valid details in [Page Name]

@TC-X002 @Review
Scenario: [Action] [Page Name] with Missing Details
	Given I have logged in with valid user credentials
	When I attempt to [action] [Page Name] with missing details
	Then I should see an validation error for the missing details in [Page Name]

@TC-X003 @Review
Scenario: [Action] [Page Name] with Invalid Details
	Given I have logged in with valid user credentials
	When I attempt to [action] [Page Name] with invalid details
	Then I should see an validation error for the invalid details in [Page Name]
```

## Model Factory Rules

**Location:** `{Tests folder}\Factories\{Page}PageModelFactory.cs`

`Default()` is **required** — it returns a model with realistic valid values and is the only method the
shipped factories (`RegistrationPageModelFactory`, `ContactUsPageModelFactory`) currently define.

Add `Empty()` and/or `Invalid()` **only when** the feature includes the corresponding validation
scenarios (Missing Details / Invalid Details). Do not add unused factory methods.

| Method | Required? | Purpose |
|---|---|---|
| `Default()` | Always | All fields set to realistic valid values |
| `Empty()` | Only with a Missing-Details scenario | Start from `Default()`, clear required fields to `""` |
| `Invalid()` | Only with an Invalid-Details scenario | Start from `Default()`, set fields to values that fail validation |

Match the shipped factory style: keep the `// TODO - Implement potential missing factory property...`
marker comment, and assign each property on its own line.

```csharp
using {Company}.{Project}.Web.Models;
using System;

namespace {Company}.{Project}.Web.Tests.Factories
{
    public class {Page}PageModelFactory
    {
        public static {Page}PageModel Default()
        {
            var model = new {Page}PageModel();

            // TODO - Implement potential missing factory property...

            model.Property1 = "valid value";
            // ... all model properties

            return model;
        }

        // Add only if a Missing-Details scenario exists:
        public static {Page}PageModel Empty()
        {
            var model = Default();
            model.Property1 = "";
            // ... clear all required fields
            return model;
        }

        // Add only if an Invalid-Details scenario exists:
        public static {Page}PageModel Invalid()
        {
            var model = Default();
            model.Property1 = "x";   // too short / wrong format
            // ... make fields invalid
            return model;
        }
    }
}
```

### Named variants replace branching

When several scenarios each need a *different* malformed input, give the factory one clearly named
method per variant rather than one method that decides. This is what lets the step definitions stay
branch-free — each step calls exactly one factory method.

```csharp
public static string CreateMalformedPetBody()
{
    // Not parsable as JSON at all.
    return "{ this is not valid json";
}

public static string CreateEmptyPetBody()
{
    // No request body at all.
    return string.Empty;
}

public static string CreateWronglyTypedPetBody()
{
    // The id property is an int64 in the schema, a string violates the type.
    return "{\"id\":\"not-a-number\",\"name\":\"Expressium-Pet\"}";
}
```

Each variant carries a one-line comment naming what it violates. Raw request-body strings belong here,
never inline in a step definition.

## Step Definition Rules

### Class structure

```csharp
using {Company}.{Project}.Web.Models;
using {Company}.{Project}.Web.Pages;
using {Company}.{Project}.Web.Tests.Factories;
using Reqnroll;
using System.Threading.Tasks;

namespace {Company}.{Project}.Web.Tests.BusinessTests.Steps
{
    [Binding]
    public class {Page}Steps : BaseSteps
    {
        private {Page}PageModel {page}PageModel;

        public {Page}Steps(BaseContext baseContext) : base(baseContext)
        {
        }

        // When steps
        // Then steps
        // Helper methods
    }
}
```

### Reuse one method across equivalent step phrasings

**Never duplicate a method body just because the Gherkin wording differs.** When two or more steps
perform the same work, stack their attributes on a **single** method.

The common case is an action that is also a precondition. `Given I have added a new pet to the store
with valid details` and `When I add a new pet to the store with valid details` describe the same
operation in different tenses — the Gherkin must read naturally in both positions, but there is only
one behaviour, so there is only one method.

Reqnroll matches `[Given]`, `[When]`, and `[Then]` attributes independently, so any combination can be
stacked. Order the attributes as they appear in the feature file.

❌ **Wrong — two methods, identical bodies:**
```csharp
[Given(@"I have added a new pet to the store with valid details")]
public async Task GivenIHaveAddedANewPetToTheStoreWithValidDetailsAsync()
{
    petService = new PetService(logger, request);
    petServiceModel = PetFactory.CreatePet();

    response = await petService.AddPet(petServiceModel);
}

[When(@"I add a new pet to the store with valid details")]
public async Task WhenIAddANewPetToTheStoreWithValidDetailsAsync()
{
    petService = new PetService(logger, request);
    petServiceModel = PetFactory.CreatePet();

    response = await petService.AddPet(petServiceModel);
}
```

✅ **Right — one method, stacked attributes:**
```csharp
[Given(@"I have added a new pet to the store with valid details")]
[When(@"I add a new pet to the store with valid details")]
public async Task WhenIAddANewPetToTheStoreWithValidDetailsAsync()
{
    petService = new PetService(logger, request);
    petServiceModel = PetFactory.CreatePet();

    response = await petService.AddPet(petServiceModel);
}
```

**Method naming when attributes are stacked.** Name the method after the primary (usually `When`)
phrasing and keep the `Async` suffix. Do not invent a neutral name that matches neither binding.

**Scope of the rule.** It applies when the bodies would be *identical*. Two steps that merely look
similar but assert different properties, call different service methods, or use different factory
variants are genuinely different steps — keep them separate. Do not collapse them by adding a
parameter and branching on it; that trades this rule for a violation of "No logical statements in
step definitions".

**Extracting a shared private helper** is the alternative when two steps share most but not all of
their work — the helper holds the common part and each step calls it. Prefer stacked attributes when
the bodies are identical; prefer a helper when they diverge.

### No logical statements in step definitions

**A step definition contains no `if`, `else`, `switch`, ternary, or loop that selects behaviour.**
Each step method is a straight sequence: build or fetch what it needs, perform the action, store the
result. One step, one behaviour.

Branching in a step is test logic hidden from the feature file. Its failure mode is silent: a `switch`
with a `default:` arm swallows any unrecognised value, so a typo in the Gherkin still runs a test —
just not the one that was written. The feature file then documents coverage that does not exist.

When two cases differ in behaviour, they are two steps, each with its own binding, each named for what
it does.

❌ **Wrong — branching on a placeholder value:**
```csharp
[When(@"I attempt to add a new pet to the store with (.*) details")]
public async Task WhenIAttemptToAddANewPetToTheStoreWithDetailsAsync(string details)
{
    petService = new PetService(logger, request);

    switch (details)
    {
        case "malformed":
            response = await petService.AddPet("{ this is not valid json");
            break;
        case "empty":
            response = await petService.AddPet(string.Empty);
            break;
        default:
            response = await petService.AddPet("{\"id\":\"not-a-number\"}");
            break;
    }
}
```

✅ **Right — one binding per behaviour, body built by the factory:**
```csharp
[When(@"I attempt to add a new pet to the store with a malformed request body")]
public async Task WhenIAttemptToAddANewPetToTheStoreWithAMalformedRequestBodyAsync()
{
    petService = new PetService(logger, request);

    response = await petService.AddPet(PetFactory.CreateMalformedPetBody());
}

[When(@"I attempt to add a new pet to the store with an empty request body")]
public async Task WhenIAttemptToAddANewPetToTheStoreWithAnEmptyRequestBodyAsync()
{
    petService = new PetService(logger, request);

    response = await petService.AddPet(PetFactory.CreateEmptyPetBody());
}
```

**Scope of the rule.** It bans logic that *chooses what the test does*. It does not ban ordinary
expressions inside an assertion — a LINQ predicate such as
`asserts.IsTrue(model.All(x => x.Status == expectedStatus), "...")` is an assertion over a collection,
not a branch, and is correct.

If a step seems to need a branch, the cause is almost always an `Examples` table that should have been
split into separate scenarios, or a factory that should have named variants.

### Code rules
- **No `#region` directives** anywhere in step files
- **No `if` / `else` / `switch` / ternary / behaviour-selecting loops** — see above
- **No duplicated method bodies** — stack `[Given]`/`[When]`/`[Then]` attributes on one method, or extract a private helper
- Model stored as **private class-level field** (camelCase: `contactUsPageModel`)
- Page objects created as **local variables** within each step method — never as class fields
- Navigation always via the main menu bar class (typically `MainMenuBar`, local variable named `mainMenuBar`) inside the When step
- Step methods that `await` anything are `async Task` and carry an **`Async` suffix** on the method name (e.g. `WhenICompleteAndSubmit...Async`). A step that performs only synchronous asserts may be `public void` with no suffix (see the synchronous Then example).
- Page object and service calls are `await`ed; asserts read an awaited getter, e.g. `asserts.EqualTo(await page.GetTitle(), ...)`
- No literal test data (raw JSON bodies, magic strings) inline in a step — it belongs in the factory
- Incomplete `Then` steps use `throw new PendingStepException()` when scaffolding; do not ship a pending step where the expected result is already known — implement it
- Do not use `throw new NotImplementedException()`
- The base class exposes `page` (UI) and `request` (API) — there is no `driver`

### When step — valid data
```csharp
[When(@"I [action] with valid details in [Page Name]")]
public async Task WhenI...WithValidDetailsIn{Page}Async()
{
    var mainMenuBar = new MainMenuBar(logger, page);
    await mainMenuBar.Click{Page}();

    var {page}Page = new {Page}Page(logger, page);
    {page}PageModel = {Page}PageModelFactory.Default();

    await {page}Page.FillForm({page}PageModel);
    await {page}Page.ClickSubmit();
}
```

### When step — missing / invalid data
Each validation case is its own step calling its own factory method — never one step that decides
which factory method to call.

```csharp
[When(@"I attempt to [action] with missing details in [Page Name]")]
public async Task WhenIAttemptTo...MissingDetailsIn{Page}Async()
{
    var mainMenuBar = new MainMenuBar(logger, page);
    await mainMenuBar.Click{Page}();

    var {page}Page = new {Page}Page(logger, page);
    {page}PageModel = {Page}PageModelFactory.Empty();

    await {page}Page.FillForm({page}PageModel);
    await {page}Page.ClickSubmit();
}

[When(@"I attempt to [action] with invalid details in [Page Name]")]
public async Task WhenIAttemptTo...InvalidDetailsIn{Page}Async()
{
    var mainMenuBar = new MainMenuBar(logger, page);
    await mainMenuBar.Click{Page}();

    var {page}Page = new {Page}Page(logger, page);
    {page}PageModel = {Page}PageModelFactory.Invalid();

    await {page}Page.FillForm({page}PageModel);
    await {page}Page.ClickSubmit();
}
```

### Then step — pending implementation
Every pending Then step MUST instantiate the page object and include a commented-out assertion
as a scaffold for the implementer. The `throw new PendingStepException()` always comes last.

```csharp
[Then(@"the [action] should be [completed] in [Page Name]")]
public async Task ThenThe...In{Page}Async()
{
    var {page}Page = new {Page}Page(logger, page);
    //asserts.EqualTo(await {page}Page.GetNotification(), "...", "Validating the {Page} notification...");

    throw new PendingStepException();
}
```

```csharp
[Then(@"I should see validation errors for the missing details in [Page Name]")]
public async Task ThenIShouldSeeValidationErrorsForTheMissingDetailsIn{Page}Async()
{
    var {page}Page = new {Page}Page(logger, page);
    //asserts.EqualTo(await {page}Page.GetNotification(), "...", "Validating the {Page} notification...");

    throw new PendingStepException();
}
```

The commented-out assertion serves as a hint to the implementer — replace the `"..."` placeholder
with the actual expected notification or error message once it is known, then remove the comment
and delete the `throw new PendingStepException()` line.

### Then step — implemented assertion
```csharp
[Then(@"I should be redirected to the Home page")]
public async Task ThenIShouldBeRedirectedToTheHomePageAsync()
{
    var homePage = new HomePage(logger, page);
    asserts.EqualTo(await homePage.GetTitle(), "Home", "Validate the HomePage title property...");
}
```

### Then step — synchronous assertion (no await)
When the assertion needs no `await` (e.g. checking an API response object already in hand), the
method may be `public void` with no `Async` suffix:

```csharp
[Then(@"the timezone service response status should be (.*)")]
public void ThenTheServiceResponseStatusShouldBe(int expectedStatus)
{
    asserts.EqualTo(response.Status, expectedStatus, "Validate the service response status...");
}
```

## Common Mistakes to Avoid

- Guessing namespaces — always derive from `Configuration.json`
- Generating BDD tests for navigation-only pages — always classify the page first
- Skipping table-based pages — a page with a public `BaseTable` property always gets a feature file
- **Generating a `Scenario Outline` with an `Examples` block — always split into separate scenarios**
- **Using a `DataTable` as a substitute for `Examples` — a DataTable is one payload, not several cases**
- **`if` / `else` / `switch` / ternary in a step definition — split into one binding per behaviour**
- **A `default:` or `else` arm silently handling unrecognised values — the typo-swallowing failure mode**
- **Raw JSON bodies or magic strings inline in a step — move them to named factory variants**
- **Two step methods with identical bodies because the Gherkin wording differs — stack the attributes on one method**
- **Collapsing two genuinely different steps by adding a parameter and branching on it — that is the step-logic violation wearing a disguise**
- **Given/When phrasings of the same action worded so differently they cannot share a method — keep them a tense apart**
- More than 5 scenarios per feature (except service/contract features — see the exception above)
- More than 1 scenario for table-based pages
- Background blocks
- Navigation steps in the feature file
- Low-level, field-by-field steps
- `#region` directives in step definitions
- Using `driver` in step code — the base class exposes `page` (UI) and `request` (API)
- Synchronous `void` step methods that call `await`-ing page/service methods — make them `async Task` with an `Async` suffix
- Page objects as class-level fields
- `throw new NotImplementedException()` — use `PendingStepException` instead
- Inline model creation in steps — always use the factory
- Only presenting files as chat output without saving them to the solution
- Pending Then steps missing the page object instantiation and commented-out assertion scaffold
- Scenario names not following Title Case for important words
- Scenario names too vague to identify the single case they cover, now that Examples rows are gone
- Noisy outcome words in scenario names ("Correctly", "Fails", "Passes") — a leading "Successful"/"Unsuccessful" qualifier is fine
- Creating a factory for table-based pages — they have no model and need no factory
